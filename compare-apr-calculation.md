# Методика расчёта APR на Aztec Staking Dashboard

## Как это работает простыми словами

APR (Annual Percentage Rate) — это ожидаемая годовая доходность от стейкинга. Дашборд показывает её как процент, который стейкер теоретически заработает за год при текущих условиях сети.

Сеть Aztec разделена на слоты длительностью 72 секунды. Расчёт APR предполагает, что каждый слот генерирует награду (`blockReward`) в размере 400 токенов AZTEC. В контракте этот параметр назван `blockReward` (награда за блок), а частота определяется через `slotDuration` (длительность слота) — код приравнивает одно к другому. Если в реальности бывают пустые слоты (без блока), фактическая доходность будет ниже расчётной.

Не вся награда идёт стейкерам. 70% (280 AZTEC) получают секвенсеры — те, кто застейкал токены и участвует в подтверждении блоков. Оставшиеся 30% уходят пруверам.

Дальше считается сколько слотов будет за год. В году 31,536,000 секунд, слот каждые 72 секунды — значит 438,000 слотов в год. Умножаем 280 AZTEC на 438,000 слотов — получаем общий годовой пул наград для всех секвенсеров: 122,640,000 AZTEC.

Этот пул делится поровну между всеми валидаторами. Считаются не только активные, но и те кто стоит в очереди на активацию — они тоже «разбавляют» награду. Если валидаторов 3,650, каждый получит примерно 33,600 AZTEC за год.

Чтобы получить процент, нужно понять доходность относительно вложения. Минимальный стейк для запуска валидатора — 200,000 AZTEC. Делим 33,600 на 200,000 — получаем 0.168, то есть 16.8% годовых.

Важно: это оценочный показатель. Он не учитывает комиссию провайдера (take rate), не учитывает реинвестирование наград (compound), и предполагает что каждый валидатор стейкает ровно минимум. Реальная доходность конкретного стейкера может отличаться.

Все параметры (`blockReward`, доля секвенсеров, длительность слота, минимальный стейк, количество валидаторов) читаются напрямую из смарт-контракта в момент запроса, поэтому APR автоматически обновляется при изменении условий сети.

## Источник данных

Все параметры читаются **live из Rollup смарт-контракта** (`0x603bb2c05d474794ea97805e8de69bccfb3bca12`) через RPC-вызовы view-функций:

| Функция | Возвращает | Текущее значение |
|---|---|---|
| `getRewardConfig()` | `{rewardDistributor, sequencerBps, booster, blockReward}` | bps=7000, reward=400 AZTEC |
| `getSlotDuration()` | `uint256` секунд | 72 |
| `getActivationThreshold()` | `uint256` в wei | 200,000 AZTEC |
| `getActiveAttesterCount()` | `uint256` | динамически |
| `getEntryQueueLength()` | `uint256` | динамически |

## Формула

```
sequencerBlockReward = blockReward * sequencerBps / 10_000
slotsPerYear         = 31_536_000 / slotDuration
totalAnnualRewards   = sequencerBlockReward * slotsPerYear
totalAttesters       = activeAttesterCount + entryQueueLength
rewardsPerValidator  = totalAnnualRewards / totalAttesters
APR                  = rewardsPerValidator * 10_000 / activationThreshold / 100
```

Словами: **годовой доход одного валидатора (только секвенсерная доля блок-реварда) делённый на минимальный стейк**.

## Определения переменных

### Параметры из контракта

| Переменная | Тип | Определение |
|---|---|---|
| `blockReward` | `uint96` | Общая награда за один блок (слот) сети в wei. Распределяется между секвенсером и бустером. Текущее значение: 400 AZTEC. |
| `sequencerBps` | `uint16` | Доля блок-реварда, которая идёт секвенсерам (стейкерам), в basis points. 10000 = 100%. Текущее значение: 7000 (70%). Остальные 30% идут через `booster` контракт. |
| `rewardDistributor` | `address` | Контракт, ответственный за раздачу наград валидаторам. В расчёте APR не используется. |
| `booster` | `address` | Контракт, получающий не-секвенсерную часть блок-реварда (100% - sequencerBps). В расчёте APR не используется. |
| `slotDuration` | `uint256` | Длительность одного слота (блока) сети Aztec в секундах. Определяет как часто генерируются блоки и начисляются награды. Текущее значение: 72 секунды. |
| `activationThreshold` | `uint256` | Минимальное количество токенов (в wei), необходимое для активации одного валидатора. Используется как знаменатель APR — «размер вложения». Текущее значение: 200,000 AZTEC. |
| `activeAttesterCount` | `uint256` | Количество валидаторов, которые прямо сейчас активны в сети и участвуют в подтверждении блоков. Читается из состояния Rollup контракта. |
| `entryQueueLength` | `uint256` | Количество валидаторов, которые внесли депозит и ожидают активации в очереди. Ещё не подтверждают блоки, но уже «разбавляют» расчётный APR. |

### Расчётные переменные

| Переменная | Определение |
|---|---|
| `totalAttesters` | `activeAttesterCount + entryQueueLength`. Все валидаторы, между которыми делятся годовые награды. |
| `sequencerBlockReward` | Часть блок-реварда для секвенсеров: `blockReward * sequencerBps / 10000`. Это та сумма, которая распределяется между стейкерами за каждый слот. |
| `slotsPerYear` | Количество слотов за год: `31_536_000 / slotDuration`. Определяет сколько раз за год начисляются награды. |
| `totalAnnualRewards` | Общий объём наград всем секвенсерам за год: `sequencerBlockReward * slotsPerYear`. |
| `rewardsPerValidator` | Годовые награды на одного валидатора при равномерном распределении: `totalAnnualRewards / totalAttesters`. |
| `aprBasisPoints` | APR в basis points (сотых долях процента): `rewardsPerValidator * 10000 / activationThreshold`. Промежуточное значение для сохранения точности в BigInt арифметике. |
| `APR` | Годовая процентная ставка: `aprBasisPoints / 100`. Отображается на дашборде с одним знаком после запятой. |

### Числовые константы

| Константа | Значение | Определение |
|---|---|---|
| `31_536_000` | `365 * 24 * 60 * 60` | Количество секунд в году (365 дней). Високосные годы не учитываются — стандартная практика для DeFi APR-расчётов. |
| `10_000` | basis points base | Базис для пересчёта basis points в проценты. 10000 bps = 100%. Используется дважды: для извлечения доли секвенсера из `sequencerBps`, и для промежуточного масштабирования при расчёте `aprBasisPoints` (чтобы сохранить точность в целочисленной BigInt арифметике). |
| `100` | percent divisor | Делитель для перевода basis points в проценты на финальном шаге: `aprBasisPoints / 100 = APR%`. |
| `0n` | fallback | Значение APR при нулевом `activationThreshold` (деление на ноль невозможно). |

## Что учитывается, а что нет

**Учитывается:**
- Только секвенсерная часть блок-реварда (70%). Остальные 30% идут через booster пруверам.
- Все валидаторы (активные + очередь). Награды делятся на всех, включая тех кто ещё в очереди.

**Не учитывается:**
- Provider take rate (комиссия провайдера) — APR показан до вычета комиссии
- Compound-эффект (реинвестирование наград)
- Пустые слоты — расчёт предполагает что каждый слот генерирует `blockReward`. Если бывают слоты без блока, реальная доходность будет ниже
- Вариативность блок-времени (используется фиксированный `slotDuration`)
- Фактический размер стейка, если он > минимума (знаменатель всегда = `activationThreshold`)

## Вычисления в BigInt

Весь расчёт идёт в `BigInt` (wei, 18 decimals). Деления целочисленные с отбрасыванием остатка. Финальное преобразование:

```typescript
aprBasisPoints = (rewardsPerValidator * 10000n) / stakingRequirement  // BigInt
apr = Number(aprBasisPoints) / 100  // обычное число с процентами
```

## Кеширование

- Результат кешируется на **30 секунд** в памяти индексера (`cachedAPR`, `CACHE_TTL = 0.5 * 60 * 1000`)
- При ошибке RPC возвращается последнее закешированное значение, или `0.0` если кеш пуст

## Расхождение APR и числа валидаторов на дашборде

APR использует `getActiveAttesterCount() + getEntryQueueLength()` **из контракта** (live RPC). Число "Total Number of Sequencers" на дашборде — это `totalDepositsCount - withdrawnCount` **из БД индексера** (исторические события). Это разные числа из разных источников, они могут расходиться из-за:

- Задержки индексации (индексер ещё не обработал свежие события)
- Валидаторов в процессе выхода (withdraw initiated, но не finalized) — контракт их уже не считает, а индексер ещё не вычел
- 30-секундного кеширования APR — за это время число валидаторов может измениться

## Пример расчёта с реальными параметрами

При текущих параметрах контракта и допущении 3,650 валидаторов:

```
sequencerBlockReward = 400 * 7000 / 10000 = 280 AZTEC
slotsPerYear         = 31,536,000 / 72 = 438,000
totalAnnualRewards   = 280 * 438,000 = 122,640,000 AZTEC
rewardsPerValidator  = 122,640,000 / 3,650 = 33,600 AZTEC
aprBasisPoints       = 33,600 * 10,000 / 200,000 = 1,680
APR                  = 1,680 / 100 = 16.8%
```

# Методика расчёта APR на ValidatorInfo

## Как это работает простыми словами

ValidatorInfo рассчитывает APR на основе **фактических данных за каждый конкретный день**, а не теоретического прогноза. Подход строится на трёх реальных показателях:

1. **Сколько блоков реально произведено за день** — запрашивается из Aztec Indexer API, который индексирует L2-блокчейн. Если в какой-то день были пропущенные слоты (секвенсер не предложил блок), это автоматически учитывается.

2. **Какая награда за каждый блок** — читается из Rollup смарт-контракта на L1 (Ethereum): `blockReward` и `sequencerBps`. Только секвенсерная доля (70%) учитывается в расчёте.

3. **Сколько токенов реально участвует в консенсусе** — восстанавливается из on-chain событий: `ValidatorQueued` (регистрация валидатора, +200,000 AZTEC), `WithdrawInitiated` (начало выхода, вычитается сумма из события), `Slashed` (слэшинг по 2,000 AZTEC за каждое событие, вычитается из стейка). Дополнительно исключаются zombie-валидаторы (баланс ниже порога ejection = 196,000 AZTEC, обычно после 3+ слэшей). Для zombie вычитается не фиксированная сумма, а их реальный `effectiveBalance` (200,000 минус сумма их слэшинга), чтобы избежать двойного учёта слэшинга.

Формула: дневные награды делятся на объём стейка, реально участвующего в генерации наград, результат умножается на 365 для аннуализации.

APR рассчитывается для каждого дня отдельно и сохраняется в таблицу `ChainAprHistory`. Это позволяет строить графики изменения APR во времени и видеть реальную историческую доходность, а не только текущий прогноз.

## Источники данных

ValidatorInfo использует **три независимых источника**:

### 1. Rollup смарт-контракт (L1 Ethereum)

| Функция | Возвращает | Использование |
|---|---|---|
| `getRewardConfig()` | `{blockReward, sequencerBps, ...}` | Награда за блок и доля секвенсера |

Вызывается через L1 RPC с failover (несколько RPC-эндпоинтов). Параметры читаются один раз на запуск пересчёта и применяются ко всем дням.

### 2. Aztec Indexer API (L2)

| Эндпоинт | Возвращает | Использование |
|---|---|---|
| `getBlockByHeight(n)` | L2-блок с timestamp | Бинарный поиск первого и последнего блока дня |
| `getLatestHeight()` | Текущая высота L2 | Верхняя граница для бинарного поиска |

Функция `countBlocksForDay(date)` выполняет два бинарных поиска по timestamp — находит первый и последний блок за конкретную дату (UTC) и возвращает `lastBlock - firstBlock + 1`.

### 3. Events Database (L1 события, синхронизированные в PostgreSQL)

| Таблица событий | Назначение в расчёте |
|---|---|
| `AztecValidatorQueuedEvent` | Регистрация валидатора → +200,000 AZTEC к стейку |
| `AztecWithdrawInitiatedEvent` | Начало выхода → вычитается `amount` из стейка |
| `AztecSlashedEvent` | Слэшинг → вычитается `amount` из стейка |

События синхронизируются из L1-контрактов отдельным job-ом (`aztec-sync-events`), который отслеживает новые события по номерам блоков.

### 4. Node Distribution History (Main Database)

| Таблица | Назначение в расчёте |
|---|---|
| `AztecNodeDistributionHistory` | Количество zombie-валидаторов за каждый день → исключаются из знаменателя APR |

Zombie-валидаторы — это валидаторы с `effectiveBalance < ejectionThreshold` (196,000 AZTEC). Они исключены из консенсуса и не получают наград.

**Важно**: из знаменателя APR вычитается **сумма effectiveBalance каждого zombie**, а не фиксированная величина за каждого. Это связано с тем, что слэшинг zombie уже учтён в `totalStaked` (через `SUM(Slashed.amount)`). Если бы мы вычитали фиксированные 200,000 за каждого zombie, слэшинг считался бы дважды.

Пример: zombie получил 3 слэша по 2,000 AZTEC = 6,000 суммарно. `totalStaked` уже вычел эти 6,000. `effectiveBalance` zombie = 200,000 - 6,000 = 194,000. Вычитаем из `totalStaked` именно 194,000. Итого из исходных 200,000 данного zombie: 6,000 (слэшинг) + 194,000 (effectiveBalance) = 200,000. Корректно.

## Формула

```
# Параметры из контракта (постоянные на момент расчёта)
sequencerBlockReward = blockReward * sequencerBps / 10_000

# Для каждого дня
realBlocksCount      = countBlocksForDay(date)               # фактические L2-блоки
totalStaked          = getTotalStakedForDay(chainId, date)    # из событий
zombieEffectiveStake = getZombieEffectiveStake(chainId, date)  # SUM(effectiveBalance) всех zombie

rewardEarningStake   = totalStaked - zombieEffectiveStake     # стейк, реально генерирующий награды
dailyRewards         = realBlocksCount * sequencerBlockReward
dailyReturn          = dailyRewards / rewardEarningStake
APR                  = dailyReturn * 365
```

Словами: **фактические дневные награды секвенсеров (реальные блоки × награда за блок × 70%), делённые на объём стейка, реально участвующего в консенсусе (без exiting и без effectiveBalance zombie-валидаторов), аннуализированные на 365 дней**.

## Определения переменных

### Параметры из контракта

| Переменная | Тип | Определение |
|---|---|---|
| `blockReward` | `uint96` | Общая награда за один произведённый блок в wei. Текущее значение: 400 AZTEC. |
| `sequencerBps` | `uint16` | Доля блок-реварда для секвенсеров в basis points. Текущее значение: 7000 (70%). |

### Расчётные переменные

| Переменная | Определение |
|---|---|
| `sequencerBlockReward` | Часть блок-реварда для секвенсеров: `blockReward * sequencerBps / 10000`. |
| `realBlocksCount` | Количество L2-блоков, реально произведённых за конкретный день (UTC). Определяется бинарным поиском по Aztec Indexer API. |
| `totalStaked` | Общий объём застейканных токенов на конец дня. Рассчитывается из on-chain событий: `(количество ValidatorQueued × 200,000 AZTEC) - SUM(WithdrawInitiated.amount) - SUM(Slashed.amount)`. Все события учитываются до 23:59:59.999 UTC целевого дня. Включает zombie (их слэшинг уже вычтен через Slashed.amount). Exiting исключены через WithdrawInitiated. |
| `zombieEffectiveStake` | Суммарный `effectiveBalance` всех zombie-валидаторов. `effectiveBalance` каждого zombie = `totalDeposits - totalSlashed` (депозиты и слэши после последнего `ValidatorQueued`). Нельзя вычитать фиксированную сумму (200k или 196k) за каждого zombie — это привело бы к двойному учёту слэшинга, который уже вычтен из `totalStaked`. Подробнее см. раздел «Слэшинг и zombie: проблема двойного учёта». |
| `rewardEarningStake` | Стейк, реально участвующий в генерации наград: `totalStaked - zombieEffectiveStake`. Из знаменателя APR исключены: exiting (через WithdrawInitiated в totalStaked) и zombie (через zombieEffectiveStake). |
| `dailyRewards` | Фактические награды за день: `realBlocksCount * sequencerBlockReward`. |
| `dailyReturn` | Дневная доходность: `dailyRewards / rewardEarningStake`. |
| `APR` | Годовая процентная ставка: `dailyReturn * 365`. Каждый день имеет свой APR, отражающий реальные условия этого дня. |

## Что учитывается, а что нет

**Учитывается:**
- Только секвенсерная часть блок-реварда (70%). Бустерная доля (30%) не включена.
- **Реальное количество блоков** за день — пустые слоты (без блока) не генерируют наград и не учитываются в расчёте.
- **Слэшинг** — вычтен из знаменателя `totalStaked`. Слэшинг уменьшает стейк, что корректно отражает реальную базу, на которую начисляются награды.
- Только валидаторы, которые **прошли ValidatorQueued** (активированы). Валидаторы в entry queue (только Deposit, без ValidatorQueued) не включены.
- Валидаторы с **WithdrawInitiated** (exiting) исключены из знаменателя APR — они не участвуют в консенсусе и не получают награды.
- **Zombie-валидаторы** (баланс < порога ejection = 196,000 AZTEC) исключены из знаменателя APR — они не участвуют в консенсусе и не получают наград. Из знаменателя вычитается `SUM(effectiveBalance)` каждого zombie, а не фиксированная сумма (чтобы избежать двойного учёта слэшинга).

**Не учитывается:**
- Provider take rate (комиссия провайдера) — APR показан до вычета комиссии.
- Compound-эффект (реинвестирование наград).
- Entry queue — валидаторы, ожидающие активации, не учитываются. В отличие от подхода Aztec Dashboard, где entry queue «разбавляет» APR.
- Изменение `blockReward` или `sequencerBps` в течение исторического периода — используются текущие значения для всех дней. Если параметры менялись, ранние дни могут быть рассчитаны неточно.

## Хранение данных

APR сохраняется **посуточно** в таблицу `ChainAprHistory`:

| Поле | Тип | Описание |
|---|---|---|
| `chainId` | `Int` | ID сети (Aztec / Aztec Testnet) |
| `date` | `DateTime` | Дата расчёта (UTC, 00:00:00) |
| `apr` | `Float` | APR за день (например, 0.168 = 16.8%) |
| `blocksCount` | `Int` | Количество реальных L2-блоков за день |
| `rewards` | `String` | Общие награды за день в wei (BigInt как строка) |
| `totalStaked` | `String` | Общий стейк на конец дня в wei (BigInt как строка) |
| `metadata` | `Json` | Параметры контракта: `{blockReward, sequencerBps}` |

Ключ уникальности: `(chainId, date)`. При повторном расчёте запись обновляется (upsert).

## Слэшинг и zombie: проблема двойного учёта

### Параметры слэшинга из контракта

| Параметр | Значение | Определение |
|---|---|---|
| `slashAmounts` | `uint256[3]` | Массив из 3 уровней слэшинга. Все 3 уровня сейчас установлены в 2,000 AZTEC (1% от activationThreshold). |
| `ejectionThreshold` | `196,000 AZTEC` | Минимальный `effectiveBalance` для участия в консенсусе. Если баланс ниже — валидатор становится zombie. Равен 98% от activationThreshold (200,000). |
| Событие `Slashed` | `{attester: address, amount: uint256}` | Содержит адрес валидатора и фактическую сумму слэша. `amount` берётся из параметра вызова `slash()`. |

### Путь к zombie-статусу

```
Начальный стейк:       200,000 AZTEC
Слэш 1 (-2,000):      198,000 AZTEC   > 196,000 → ещё active
Слэш 2 (-2,000):      196,000 AZTEC   >= 196,000 → ещё active
Слэш 3 (-2,000):      194,000 AZTEC   < 196,000 → ZOMBIE
```

Минимум 3 слэша по 2,000 AZTEC (суммарно 6,000 AZTEC) нужно для перехода в zombie-статус.

### Почему нельзя вычитать фиксированную сумму за zombie

`totalStaked` рассчитывается как:
```
totalStaked = SUM(ValidatorQueued × 200,000) - SUM(WithdrawInitiated.amount) - SUM(Slashed.amount)
```

Слэшинг zombie **уже учтён** в `SUM(Slashed.amount)`. Если мы вычтем ещё 200,000 (или 196,000) за каждого zombie, слэшинг посчитается дважды:

```
# НЕПРАВИЛЬНО: zombie × 200,000
# Для zombie с 3 слэшами по 2,000:
# В totalStaked: -6,000 (слэшинг)
# Дополнительно: -200,000 (zombie)
# Итого вычтено из исходных 200k: 206,000 ← БОЛЬШЕ ЧЕМ СТЕЙК!

# НЕПРАВИЛЬНО: zombie × 196,000
# В totalStaked: -6,000 (слэшинг)
# Дополнительно: -196,000 (zombie)
# Итого: 202,000 ← тоже больше чем стейк

# ПРАВИЛЬНО: zombie × effectiveBalance
# В totalStaked: -6,000 (слэшинг)
# Дополнительно: -194,000 (effectiveBalance = 200,000 - 6,000)
# Итого: 6,000 + 194,000 = 200,000 ← ровно весь стейк zombie ✓
```

### Реализация

`effectiveBalance` каждого zombie рассчитывается через `getValidatorBalances()` из `get-zombie-validators.ts`:

```typescript
effectiveBalance = totalDeposits - totalSlashed
// где totalDeposits и totalSlashed считаются для событий ПОСЛЕ lastQueuedBlock валидатора
```

Для APR-расчёта: `rewardEarningStake = totalStaked - SUM(zombie.effectiveBalance для всех zombie)`.

## Синхронизация с tokenomics

После обновления истории, `syncAprToTokenomics()` берёт **последнюю запись** из `ChainAprHistory` и записывает её APR в таблицу `tokenomics`, откуда значение попадает на фронтенд.

# Сравнение методик: Aztec Staking Dashboard vs ValidatorInfo

## Сравнительная таблица

| Аспект | Aztec Staking Dashboard | ValidatorInfo |
|---|---|---|
| **Тип расчёта** | Теоретический прогноз (snapshot) | Фактический исторический (per-day) |
| **Количество блоков** | Теоретическое: `секунд_в_году / slotDuration` | Реальное: `countBlocksForDay()` из Aztec Indexer |
| **Знаменатель APR** | `(activeAttesterCount + entryQueue) × activationThreshold` | `(ValidatorQueued × 200k - WithdrawInitiated - Slashed) - SUM(zombie_effectiveBalance)` |
| **Слэшинг в знаменателе** | Не учитывается | Вычтен из totalStaked |
| **Entry queue** | Включена (разбавляет APR) | Не включена |
| **Exiting валидаторы** | Исключены (контракт не считает их active) | Исключены (через WithdrawInitiated) |
| **Zombie валидаторы** | Исключены (контракт не считает их active) | Исключены (через AztecNodeDistributionHistory) |
| **Пустые слоты** | Не учитываются (100% uptime) | Учитываются (реальные блоки) |
| **Гранулярность** | Единственное значение «сейчас» | Отдельное значение за каждый день |
| **История** | Нет | Таблица `ChainAprHistory` с графиками |
| **Обновление** | Каждые 30 секунд (live RPC) | Ежедневно (cron job) |
| **Источник кол-ва валидаторов** | Live из контракта | Из синхронизированных L1-событий |

## Почему расчёт ValidatorInfo точнее

### 1. Реальные блоки вместо теоретических слотов

Aztec Dashboard предполагает, что **каждый слот генерирует блок и награду**. В контракте награда называется `blockReward` (награда за блок), а не `slotReward`. Награда начисляется только за произведённый блок. Если секвенсер пропустил слот — блока нет, награды нет.

ValidatorInfo считает **фактическое количество L2-блоков** за день через Aztec Indexer API. Если из 1,200 теоретических слотов (86,400 сек / 72 сек) реально произведено 1,150 блоков — мы используем 1,150. Aztec Dashboard использует 1,200.

**Результат**: Aztec Dashboard систематически **завышает** APR на процент пропущенных слотов. При 95% uptime разница составляет ~5% от APR.

### 2. Слэшинг учтён в знаменателе

Когда валидатор получает слэш, его стейк уменьшается. Размер слэша — 2,000 AZTEC (1% от activationThreshold = 200,000). Если валидатор получил 3 слэша (суммарно 6,000 AZTEC) — эффективный стейк теперь 194,000 AZTEC, что ниже порога ejection (196,000), и валидатор становится zombie.

ValidatorInfo **вычитает все суммы слэшинга** из `totalStaked`. Это означает, что знаменатель APR отражает реальный объём капитала, на который начисляются награды.

Aztec Dashboard использует фиксированный `activationThreshold` (200,000 AZTEC) для каждого валидатора, **игнорируя слэшинг**. При наличии слэшинга в сети их знаменатель завышен → APR занижен.

**Результат**: ValidatorInfo точнее отражает реальную доходность на единицу застейканного капитала.

### 3. Zombie-валидаторы исключены из знаменателя (с учётом двойного счёта)

Zombie-валидаторы — это секвенсеры, чей `effectiveBalance` упал ниже порога ejection (196,000 AZTEC) из-за слэшинга. Они **исключены из консенсуса**: не могут предлагать и атестовывать блоки, не получают наград. Но их токены всё ещё залочены в контракте.

ValidatorInfo исключает zombie из знаменателя APR, вычитая **сумму effectiveBalance каждого zombie**, а не фиксированную величину. Это принципиально важно: слэшинг zombie уже учтён в `totalStaked` (через `SUM(Slashed.amount)`), поэтому вычитание фиксированных 200,000 или 196,000 за каждого zombie привело бы к двойному счёту. Вычитая `effectiveBalance` (= 200,000 - totalSlashed), мы корректно убираем из знаменателя ровно те токены, которые принадлежат zombie, без повторного учёта их слэшинга.

Aztec Dashboard тоже исключает zombie через `getActiveAttesterCount()` контракта — но только для текущего момента. ValidatorInfo делает это **для каждого исторического дня**.

**Результат**: Знаменатель APR точнее отражает капитал, реально генерирующий награды, в каждый конкретный день, без арифметических ошибок двойного учёта.

### 4. Историческая гранулярность

Aztec Dashboard показывает **одно число** — APR прямо сейчас при идеальных условиях. Если вчера сеть работала на 80% uptime, а сегодня на 100% — вчерашний APR потерян. Невозможно увидеть тренд или сравнить периоды.

ValidatorInfo хранит **APR за каждый день** в `ChainAprHistory`:
- Можно строить графики изменения APR во времени
- Видно влияние событий сети (слэшинг, массовый вход/выход валидаторов) на доходность
- Можно рассчитать средний APR за произвольный период (7 дней, 30 дней, 90 дней)

**Результат**: Пользователь получает полную картину доходности, а не мгновенный снимок.

### 5. Токен-взвешенный знаменатель вместо плоского

Aztec Dashboard считает знаменатель как `количество_валидаторов × 200,000`. Это предполагает, что каждый валидатор стейкает ровно минимум.

ValidatorInfo строит знаменатель из **реальных сумм событий**: каждый `ValidatorQueued` добавляет 200,000, но вычитаются **фактические суммы** из `WithdrawInitiated.amount` и `Slashed.amount`. Если валидатор вышел с 194,000 (после 3 слэшей по 2,000) — из WithdrawInitiated вычитается именно 194,000, а 6,000 слэшинга уже вычтены ранее через Slashed.amount.

**Результат**: Более точный знаменатель, особенно при наличии слэшинга и выходов.

### 6. Аудируемость и воспроизводимость

Aztec Dashboard читает live-состояние контракта. Через минуту состояние может измениться — результат нельзя воспроизвести.

ValidatorInfo хранит для каждого дня: `blocksCount`, `rewards`, `totalStaked`, `metadata` (параметры контракта). Любой расчёт можно **проверить и воспроизвести**: `APR = (rewards / totalStaked) * 365`, все компоненты сохранены.

**Результат**: Прозрачность и возможность аудита исторических данных.

## Где Aztec Dashboard иначе (и это может быть обоснованно)

### Entry queue разбавляет APR

Aztec Dashboard включает entry queue в знаменатель: `totalAttesters = active + entryQueue`. Логика: валидаторы в очереди скоро активируются и начнут «разбавлять» награды. Это делает APR **более консервативным** — показывает доходность с учётом «incoming dilution».

ValidatorInfo не включает entry queue, потому что эти валидаторы **ещё не получают наград**. Наш APR показывает доходность для уже активных валидаторов.

Оба подхода имеют смысл — это вопрос определения: «APR для тех, кто уже стейкает» vs «APR с учётом разбавления от тех, кто скоро войдёт».

### Live-обновление vs дневная гранулярность

Aztec Dashboard обновляет APR каждые 30 секунд — пользователь видит актуальное значение «прямо сейчас».

ValidatorInfo рассчитывает APR раз в день (cron job). В течение дня показывается APR предыдущего дня. Для пользователя, принимающего решение о стейкинге на месяцы, дневная гранулярность достаточна. Для трейдера, реагирующего на мгновенные изменения — нет.

## Итоговая оценка

| Критерий | Aztec Dashboard | ValidatorInfo |
|---|---|---|
| Точность числителя (награды) | Теоретическая, завышена | **Фактическая, точная** |
| Точность знаменателя (стейк) | Упрощённая, без слэшинга | **Точная, с учётом слэшинга и effectiveBalance zombie** |
| Историческая глубина | Отсутствует | **Полная, посуточная** |
| Воспроизводимость | Невозможна | **Полная аудируемость** |
| Оперативность | **30 секунд** | 1 день |
| Консервативность (entry queue) | **Более консервативный** | Менее консервативный |

**Вывод**: Для исторического анализа и принятия обоснованных решений о стейкинге ValidatorInfo предоставляет значительно более точные и верифицируемые данные. Aztec Dashboard лучше подходит для мгновенного ориентира «что сейчас», но систематически завышает APR из-за допущения 100% uptime, игнорирования слэшинга и отсутствия исторической глубины.
